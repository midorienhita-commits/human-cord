## 0. なぜ書くか — 同期ではなく調和

「同期(両端が同じ状態に揃う)」ではなく「調和(役割が違うまま矛盾しない)」を選ぶ。
これはプロジェクト第三条「AI と人は役割を分ける」の言い換えでもある。
本メモの設計判断はすべてこの原則に従う:

- **AI は「目」**(歪み・光・部分欠損に強い読み取り = 頑健性)
- **cord は「約束」**(暗号的保証 = 真正性・改ざん検知・新鮮性)

AI に保証を負わせない。AI が賢くなっても約束は変わらない。これが計算非依存性の原則と地続き。

## 1. 何をするチャネルか

cord(の本質的な証明: 署名・ハッシュ・nonce・潜在チャネル)を **デジタル線を一切通さず**、

```
  発行側デバイス画面/印刷物  ──(光)──>  受信側スマホのカメラ + 端末内 AI 解析  ──> cord 復元 + 検証
```

という **光チャネル(air-gap optical channel)** に乗せる。
QR の発展形だが、担体を「QR の硬い格子」に限定せず、AI 読取を前提に
**より有機的・冗長・風景溶込み(柱2)な担体**を許す点が肝。

### 想定ユースケース
- ネットワークが無い/信用できない現場(消去作業現場・オフライン監査)での真正性受け渡し
- 「その場に物理的に居た」ことの証明(物理的présence)
- デジタル MITM が成立しない経路がほしいとき(経路がカメラと光だから)

## 2. 脅威モデル(ここが本当の急所)

| 脅威 | 光チャネル自体で防げるか | 防御の置き場所 |
|---|---|---|
| 盗聴(撮られる) | ✗ | 担体に秘密を載せない。表は検証可・裏は柱6 潜在チャネルで発行者のみ可読 |
| 改ざん(画像を加工) | △(AEAD タグで検知) | 柱9 AEAD + 卵の鎖。割れたら型(seq)だけ露出(柱10) |
| **リプレイ(再表示・再撮影で複製)** | **✗** | **プロトコル側**: 柱10 ratchet + freshness(nonce/時刻) + 柱8 煙 |
| 担体すり替え | △ | 発行者署名(柱4 片割れ)。秘密無しに正しい担体を作れない |

> **最重要の切り分け:** 光チャネルはリプレイを防げない。
> 画面を撮った画像はそのまま再表示・再撮影できる。
> → **チャネルでなくプロトコルで守る**。
> 具体的には ① cord に発行時刻多軸(柱1 kdf の公開軸)と一回限り nonce を載せ、
> ② 受信側が「未使用 nonce か」「鮮度窓内か」を検証し、
> ③ 既使用/期限切れを検知したら柱8 SmokeLog に煙を上げる。

## 3. 担体設計(AI 読取前提)

### 3.1 容量見積り
cord の本質ペイロードは小さい:

- AES-GCM タグ 16B + tip ハッシュ 32B + kdf 公開軸(数十B) + nonce 16B + (任意)潜在チャネル ≒ **数百 B 〜 数 KB**
- QR(version 40, M)で ~2.9KB。映像(複数フレーム)にすれば桁が増える。
- → **帯域は足りる。** 静止 1 枚で本質、動画でフルペイロード。

### 3.2 担体の層構造(3 層、目玉文字の発展)
```
  L1 風景層(柱2)   … 人間の目には「ただの図/紋様/写真」。可読構造を持つ(目玉文字)
  L2 潜在層(柱6)   … 発行者だけが読める裏メッセージ(L1 に溶け込む)
  L3 検証層(柱9/4) … AEAD タグ・卵の鎖 tip・発行者署名。AI が抽出し cord として検証
```
L1 が人間向け、L3 が機械向け、L2 が発行者専用。**3 つの読者(人/AI/発行者)が役割分担** = 調和。

### 3.3 AI の役割(再掲・厳密化)
- AI は L3 の**抽出器/誤り訂正器**。傾き・照明・部分欠損・モアレに対する頑健性を担う。
- AI は復号鍵を持たない・検証判定を下さない。判定は `open`/`verifyTally`/`guardedOpen` が行う。
- Fuzzy Extractor(柱4/7 `src/fuzzy.js`)の発想と接続: 「曖昧な観測 → 誤り訂正 → 確定値」。
  生体の代わりに**光学観測の曖昧さ**を fuzzy 入力として扱えるか、は Phase 2 の検討点。

## 4. プロトコル骨子(擬似)

```
発行 (emit):
  cord = seal(payload, secret, ctx, { axes, nonce })   // 柱9/1/4 既存
  cord = embedSubliminal(cord, secret, 裏メッセージ)      // 柱6 既存(任意)
  carrier = render(cord)                                // ★Phase 2 新規: cord -> 視覚担体(L1+L2+L3)
  display(carrier) または print(carrier)

受信 (receive):
  frames = capture(camera)
  cord'  = extract(frames)                              // ★Phase 2 新規: AI 抽出 + 誤り訂正 -> cord
  if not fresh(cord'.nonce, cord'.kdf.epoch): 
        smokeLog.raise('replay-or-stale', …); reject    // 柱8/10
  text   = guardedOpen(cord', secret, smokeLog)         // 柱9/4/8/10 既存
```

★ が Phase 2 で新規に書く 2 関数 = `render`(cord→担体)と `extract`(担体→cord)。
**既存 9 柱には触らない**。視覚チャネルは既存 cord を包む薄い物理層ラッパとして足す。
これが「役割を分ける」= 既存の約束を壊さず、目(物理層)だけ増設する設計。

## 5. Phase 2 での実装単位(進捗)
1. ✅ `src/visual.js` — `render(cord) -> carrier` / `extract(carrier) -> cord`。
   依存ゼロを守るため担体は**媒体非依存のテキストフレーム**(`HC1|len|cksum|base64url`)。
   実ピクセル/QR は載せず「この文字列を将来 QR/画像/印刷に乗せる」アダプタ境界として確定。
2. ✅ freshness — `seal` 無改造で実現。**nonce = `cord.tip`(seal ごと一意)**、
   **鮮度窓 = `cord.kdf.epoch`(公開軸)**。どちらも cord が既に表に出していた公開情報。
3. ✅ リプレイ検知 → `SmokeLog` 連携(`replay-or-stale` イベント型)。`FreshnessGuard` + `receiveVisual`。
4. ⏳ 担体の風景層(L1)/潜在層(L2)を AI 抽出に耐える形へ(QR → 有機担体は最後)。
5. ✅ デモ `examples/visual-demo.js`(発行 → 担体化 → ノイズ検知 → リプレイ/鮮度切れ拒否)。
6. ✅ ECC(誤り訂正)= `src/ecc.js`(Reed-Solomon over GF(256), 依存ゼロ, fuzz 済)。
   視覚担体に **HC2** として統合(`renderEcc`、`extract` が HC1 検知 / HC2 訂正を自動判別)。
   担体ノイズ・バースト・部分欠損を訂正し、能力超過は checksum で安全に拒否。デモ `examples/ecc-demo.js`。
7. ✅ **実ピクセルアダプタ = `src/image.js`(2026-06-03, 依存ゼロ=`node:zlib` のみ)。§5.4 の一周を閉じた。**
   `renderImage(cord) -> 実 PNG`(白黒2値モジュール格子)/ `extractImage(png) -> cord`。
   HC2 と同じ RS を本体に使い、`simulateOptics`(ぼけ・露出ずれ・塩胡椒ノイズ・部分遮蔽)で
   撮影劣化を模す。デモ `examples/image-demo.js`(`npm run demo:image`)、test/image.test.js 9 本。
   - **2値モジュール**を採るのは QR と同じ理由(多値グレーは実光学で潰れる)。中心サンプリング+固定しきい値。
   - **ヘッダ**(本体 RS バイト長)は別の小 RS(nsym=10)で保護。本体は encodeBlocks 出力そのもの。
   - **発見(2026-06-03): ブロックインターリーブが部分遮蔽(影・指・反射=§2 本命脅威)に効く。**
     非インターリーブだと連続領域の破損が特定 RS ブロックに集中して 16B/255 能力を即超過する。
     QR と同じく全ブロックへ撒く(画像層だけの並べ替え・ecc.js 無改変)と、隅 6% 遮蔽でも復元できた。
   - 媒体エラー(RS 訂正能力超過)は `ImageCarrierError` として安全に弾き、改ざん(AEAD=`CordTamper`)と
     混同しない=媒体層と暗号層が別ドメインであることをデモ④で実証。
8. ✅ **カメラ写真アダプタ = `src/photo.js`(2026-06-03, 依存ゼロ=`node:zlib` のみ)。「傾き/透視・finder」を実装。**
   image.js が「位置・尺度・向きが既知の格子」前提なのに対し、実カメラ写真は位置・回転・傾き(透視)が未知。
   `renderScannable(cord)`=四隅に finder(位置検出パターン)を足した実 PNG / `simulatePhoto(png,…)`=回転・
   透視(keystone)・並進・背景・光学劣化を模す(実カメラの前段)/ `scanPhoto(png)`=finder 検出 → ホモグラフィ
   補正 → モジュール再標本 → `matrixToCord`(HC2 と同じ RS)。デモ `examples/photo-demo.js`(`npm run demo:photo`)、
   test/photo.test.js 9 本。image.js は `cordToMatrix`/`matrixToCord`/`encodePng`/`decodePng` を export して再利用。
   - **自前 CV(依存ゼロ)**: Otsu 2値化 / 連結成分(4近傍 flood)/ ホモグラフィ(4点・8元ガウス消去)/
     バイリニア標本。重い CV ライブラリは持ち込まない(北極星: 鉄板技術のみ)。
   - **N(データ辺長)discovery**: finder 間隔と面積からの推定 + ヘッダ magic+RS が通る候補をブルートフォースで採る
     (誤 N は乱数同然 → magic(0x48)+版+RS+本体RS+JSON を全通過する確率は無視できる=自己修正が安全に成立)。
     **発見**: finder の bbox 幅は回転で √2 方向に膨らむ(過大推定)→ modulePx は**面積から**(回転不変)。
   - **検証済み射程(初版)**: 面内回転 ≲±40°(四隅 finder が同一形=向きの曖昧性が ±45° の理論限界)、透視 keystone ≲30%、
     ぼけ/露出ずれ/ノイズ複合まで(本番相当 N≈136 で全通過)。巨大 payload(N≈300)+強透視は遠側モジュールが
     2px 級になり解像限界。境界超は `PhotoError` で安全に失敗。写真を抜けても改ざんは AEAD が検知(デモ④)。
9. ✅ **キラリティで向き曖昧性を破る(2026-06-04・種 `docs/seed-bio-analogies.md` §3 を実装)。回転 ±45° 限界を撤廃 → 全方位 0–360°。**
   発想は二重らせんのキラリティ(右巻き/左巻き=回転対称を持たない)。担体に**向きの非対称性**を埋め、四隅同形 finder の限界を外す。
   - **TL リング(キラリティ標識)**: TL の finder だけ中央に穴を空けた「リング」にする。**重心(黒画素の質量中心)が穴の中央=白**
     に落ちる ⇒ 重心ピクセルの白/黒で「どれが物理 TL か」を一意判定。穴は中央対称なので**回転・尺度・透視に不変な
     トポロジー特徴**(面積や向きに依らない)。残り 3 隅を重心まわりの角度順に並べ [TL,TR,BR,BL] を確定。
   - **finder 選択を凸包に変更**: データ領域は 4 finder の成す四角形の**内部** ⇒ 全候補の**凸包頂点が finder**。
     凸包は重心非依存で回転・透視に頑健。旧「最遠 4 点」法は重心がビット分布で偏ると finder を取りこぼし断続失敗していた。
     `x±y` 極値法の 45° 退化(2 隅が同点)も解消。fill しきい値は 0.5→0.35(リングは 45°で fill≈0.41 まで下がるため)。
   - **検証済み射程(更新)**: 面内回転 **0–360°全周**(15°刻み 24/24)+ 鏡像(裏返し)対応(順/逆の巡回順を両試行)、
     透視 keystone ≲30%・複合劣化まで(本番相当 N≈136 で全通過)。テスト 139→140、test/photo.test.js 10 本。
   - **継続(別腹・依存/ハード が要る)**: 実カメラ撮影・端末内 AI 抽出(有機担体 L1/L2)、複数点標本+多数決での
     高 N 頑健化、動画フレーム ratchet(録画リプレイ耐性=種 §2 テロメア)。

> **副産物の発見(2026-05-29):** 視覚チャネルが**初の実 JSON 輸送経路**になり、
> `egg.js` の `hashEgg`/`openEgg` が JSON 復元後の `{type:'Buffer'}` を吸収しない潜在バグを露出
> (`cord.js` の `toBuf` 保険は比較 2 箇所のみで不完全)。
> メモの原則どおり**コアは無改変**とし、`visual.extract` 側で `reviveBuffers` してバイト忠実復元。
> 将来コア側でも JSON 往復を正式サポートするなら egg.js の正規化を検討(別タスク候補)。

## 6. 非目標(やらないこと / 誤解の予防線)
- AI に暗号判定をさせない(頑健性のみ)。
- 光チャネルでリプレイを防ごうとしない(プロトコルで防ぐ)。
- 担体の見た目の美しさ(有機化)を先にやらない。まず素朴 QR で一周を通す。
- 新しい暗号プリミティブを発明しない(計算非依存性の原則: 鉄板技術のみ)。

## 7. 開かれた問い
- 光学観測の曖昧さを Fuzzy Extractor の入力に出来るか(柱4/7 と柱7 の合流点)。
- 動画フレーム間 ratchet(柱5)で「生きている担体」= 録画リプレイ耐性を作れるか。
- 印刷物(完全オフライン・電源不要)まで射程に入れるか = 物理層の最果て。
- ~~向きの曖昧性(四隅同一形 finder の ±45° 限界)を外せるか~~ → ✅ 解決(§5.9 TL リング=キラリティで全方位)。
- 高 N + 強透視の解像限界を、複数点標本 + 多数決や適応 SCALE で押し上げられるか(§5.8 photo.js 継続)。
- `scanPhoto` の自前 CV(Otsu/連結成分/ホモグラフィ)を、実カメラ画像(実照明・実レンズ歪み)へどこまで持っていけるか。
