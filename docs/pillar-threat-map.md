# 柱の三行棚卸し(脅威 → 機構 → 性質)

> 目的: 各柱を**メタファー抜き**で「脅威T → 機構M → 性質P」の三行に落とし、
> 標準仕様・白書の一文に耐えるかを判定する。**メタファーが要求した柱**(脅威で説明できない柱)を
> 削る/格下げ/吸収する地図。標準は足し算でなく**引き算**で強くなる。
> 関連: 外部視点レビュー(memory `human_cord_outside_angle_review`)。

判定ラベル: ✅コア / ⭐固有価値(署名では出せない) / 🎯ユースケース本命 / 🧊今は不要(野心・別腹) / ✂️柱でない(格下げ/吸収)

---

## 柱1 多軸鍵生成 `kdf.js`
- **T**: 固定鍵の長期・大量使用による鍵解析。だが検証側が鍵を再現できないと検証不能。
- **M**: 公開ソルト(発行時刻 epoch/weekday/hour/parity を平文保存)+ 発行者秘密を HKDF で結合 → 発行専用コードブック。
- **P**: 発行ごとに異なる鍵素材。公開ソルトで検証再現可、秘密なしでは導出不能(片側秘匿)。
- **判定 ✅コア(ただし簡約)**: 本質は "public-salt + secret-IKM の HKDF ドメイン分離"。`weekday/parity` 等の「多軸」意味論は検証再現にしか使わないなら**公開 nonce/salt に簡約できる**。命名 "干支/時計" は不要。

## 柱9 封じのコア `egg.js`
- **T**: 文書本体の改ざん・部分差し替え・順序入替。
- **M**: AES-256-GCM(AEAD)+ ハッシュチェーン。
- **P**: 機密性 + 完全性 + 順序保証。
- **判定 ✅コア**: 標準的 AEAD+チェーン。メタファー不要、機構は本物。

## 柱5 鍵前進 `ratchet.js`
- **T**: 鍵漏洩時の過去文書の遡及解読(前方秘匿)、同一鍵の再利用。
- **M**: HMAC ベース一方向 ratchet(単位ごとに鍵が進む)。
- **P**: 現在状態が漏れても過去鍵は復元不能。
- **判定 ✅コア(用途要吟味)**: 機構は健全。ただし ratchet はストリーム/セッション向け概念。**証明書1通に複数単位の前進が要るか**は疑問(オーバーキルの可能性)。

## 柱10 最小開示 `cord.js`
- **T**: 改ざん検知時の例外/エラーから鍵・平文・内部状態が漏れる(サイドチャネル)。
- **M**: `CordTamper` は `seq`(型)のみ載せ核は載せない。ratchet 一方向。
- **P**: 失敗しても秘密は漏れない(fail-closed・minimal disclosure)。
- **判定 ✂️設計原則へ格下げ**: これは独立機能でなく**全柱に課す横断不変条件**。「柱10」でなく全体の設計原則として記述すべき。

> 上の ✅×3 + 設計原則は実体として **1つの「対称発行コア(seal/open)」** に束ねられる(`cord.js`/`egg.js`)。
> = 4柱ではなく **1コア + 3不変条件**。標準仕様ではここを最小核として切り出す。

## 柱3 秘匿突き合わせ `tally.js`
- **T**: 同一案件の複数文書を第三者が勝手に関連付け/突き合わせる、または別案件・別発行者を正規の関連と偽装。
- **M**: HMAC 通行手形(docId + 発行者秘密)。同一発行者・同一 docId なら `+` 統合、不一致なら `-` 差分。
- **P**: 発行者秘密を持つ者だけが案件内関連付けを検証・実行できる。
- **判定 ⭐固有価値**: **署名では出せない秘匿突き合わせ**。残す。注: POC は HMAC、白書は BLS 集約署名 → ビジョンと実装の乖離を正直に書く。

## 柱4a 対称発行コア `cord.js`
- **T**: 誰でも証明書を発行できてしまう(偽造)。
- **M**: 発行者秘密で seal。秘密なしではコードブック・通行手形を再現不能。
- **P**: 発行者媒介の真贋(秘密を持つサーバだけが真贋判定)。
- **判定 ✅コア**: 対称コアの中心。

## 柱4b 閾値発行 `shard.js` / `threshold.js`
- **T**: 単一拠点・単一者による単独偽造。
- **M**: 二層に正直に分ける。
  - **4b-i 対称担体の分散保管** `shard.js`/`issueWithShares`: Shamir(GF256)で発行者秘密を n 片に分割、k 片で復元してから seal。**復元の一瞬に 1 ノードへ完全な秘密が顕在化する**=対称鍵で seal する以上これは不可避(AEAD は鍵そのものを要する)。これは「閾値**署名**」ではなく秘密の情報理論的な分散**保管**。
  - **4b-ii 公開 attestation の真の閾値署名** `threshold.js`: FROST 方式のしきい値 Schnorr(素数体 DLOG 群・native BigInt・依存ゼロ)。各拠点が出すのは g^{r_i} と部分応答 z_i のみで **秘密 x は署名のどの瞬間にも再構成されない**。検証は公開鍵 y だけ(g^z==R·y^c)。単一鍵 Schnorr とバイト同一=単一発行者公開検証(柱4d)の k-of-n 版。
- **P**: 4b-i=閾値未満では情報理論的に復元不能(計算無限でも不可)。4b-ii=**単一拠点では正規署名を作れない**が文字どおり成立(k 未満の連合の補間値 ≠ x、Shamir 完全秘匿/DL 困難に帰着)。
- **判定 ⭐固有価値**: 多者発行は署名単体では出せない。残す。**真の閾値署名は 4b-ii(threshold.js)で実装到達**(公開準備レビュー H-2 を framing でなく実装で解消)。正直な限界: 単一 nonce 版は逐次・非並行セッション専用(並行=ROS/Drijvers も、同じ nonce の単純再利用も片漏洩につながる=Schnorr 系共通。並行対応の FROST 二重 nonce バインディングは将来)・k>=2 必須・信頼ディーラ(DKG は将来)・identifiable abort/VSS は将来・非定数時間。

## 柱4d 公開鍵検証層 `pubkey.js`
- **T**: 発行者媒介だと検証に発行者(秘密)が要り、第三者がオフライン独立検証できない。
- **M**: Ed25519 署名。公開可能な事実に発行者署名、公開鍵で誰でも検証。
- **P**: 公開・オフライン・第三者検証(秘密不要)。
- **判定 🎯ユースケース本命**: 証明書=長期・公開・反復検証の文書には**これが本命**。`examples/verify.html` の土台。前面に出す。

> ⚠️ **柱4は肥大している。** 4a(対称コア)/4b(閾値)/4d(公開鍵)は**別々の柱に分割すべき**。
> 一つの "柱4" に異なる機構を 3〜4 個詰めるのは標準仕様として不明瞭。

## 柱4c 人間の曖昧さを鍵源に `fuzzy.js`
- **T**: 鍵の保存・漏洩、計算による鍵取得。
- **M**: Fuzzy Extractor。生体(手相/虹彩)の曖昧さ + 誤り訂正で鍵再生、テンプレ非保存。
- **P**: 突破に物理的な本人が必要(計算非依存)。
- **判定 🧊今は不要(野心)**: 機構は学術的に本物。だが**証明書ユースケースに今は未接続**(BiosGuide は生体を使わない)。別腹・将来。

## 柱7 物理担体 `visual.js` / `audio.js` / `ecc.js` / `freshness.js`
- **T**: デジタル文書が物理媒体(紙/画面/音)を経由する際の担体ノイズ・部分欠損・リプレイ。
- **M**: 媒体非依存 frame codec(HC2 = Reed-Solomon ECC)、視覚/音響2担体、nonce 一回性 + 鮮度窓 + 煙でリプレイ防止。
- **P**: 物理担体を経ても核を復元でき、改ざん/リプレイを検知。
- **判定 ⭐固有価値(内部分岐)**: **最も distinctive**。ただし用途で割れる ——
  - 担体 codec(ECC 物理輸送)= ⭐残す。
  - リプレイ防止(鮮度窓/tip 一回性)= 🧊**チャネル/トークン専用**。証明書(長期文書)には不適用(verify-cert は意図的に外した)。

## 柱6 潜在チャネル `subliminal.js`(6-i)/ `simmons.js`(6-ii)
- **T**: 発行者だけが読める裏情報を、表の検証に影響せず公開物へ埋めたい。
- **M**: 二層に正直に分ける。
  - **6-i 付帯 authenticated ペイロード** `subliminal.js`: cord に**別フィールド**を足し keystream XOR + HMAC。**署名の自由度に埋めていない=厳密には subliminal channel ではない**(発行者のみ読める付帯チャネル)。
  - **6-ii 真の Simmons 潜在チャネル** `simmons.js`: 裏を**署名の乱数自由度(nonce)に埋める**原典構成。素数体 DSA(threshold.js 群を再利用)・**署名 (r,s) に付帯フィールド無し**・看守(公開鍵だけ)には正直署名と区別不能(covert を載せた nonce を**切り詰め棄却抽出で厳密一様化**→mod-q バイアス無し→PRF 安全性に帰着、chi-square で実証)。識別不能性は (r,s) 分布レベルで無条件成立。本文には毎回 salt を付すので**本文レベルは「全署名に salt」運用規約**前提(cover 署名 signSalted も同形式・salt は一様乱数=手がかりにならない)=レビュー指摘の salt-suffix distinguisher を塞ぐ。署名鍵 x + 別の潜在鍵を持つ者だけが nonce 復元で読む。
- **P**: 発行者秘密(+潜在鍵)を持つ者だけが裏を読める。表(公開検証)は無影響。
- **判定 🧊今は不要 + ⚠️監査で警戒される**: **6-ii で機構は本物に到達(H-3 を framing でなく実装で解消・2026-06-09)**。だが現統合で未使用、かつ subliminal/隠れチャネルは標準化・監査文脈ではむしろ**警戒対象** → 既定 OFF・標準コア(層 I〜III)から隔離(層 IV)・採用面 API には出さない。正直な限界: broadband=受信者が署名鍵 x を共有(=受信者も署名可)/narrowband・目玉文字埋込は将来/nonce 再利用は x 漏洩/受動的看守のみ/非定数時間。

## 柱8 改ざんの煙 `smoke.js`
- **T**: 改ざんが痕跡を残さず後から否認される。
- **M**: 改ざん検知を append-only ハッシュチェーンログに記録(遡及改ざん不能)。
- **P**: 改ざんの事実が消せない監査証跡として残る。
- **判定 ✂️運用規約へ吸収**: 本質は "tamper-evident audit log" = 既存のハッシュチェーン/transparency log。BiosGuide では `work_logs` に流す=**既存監査ログに吸収済**。独立柱というより「検知を監査ログに出す」運用規約。

## 柱2 表示溶込み `eyeglyph.js`
- **T**: (書けない)。README 自身が「表示用レイヤー・**検証非依存**」と明記。
- **M**: 目玉文字置換(人間向け表示)。
- **P**: 検証に一切寄与しない。
- **判定 ✂️柱でない(最有力の削る候補)**: 脅威 T が書けない=セキュリティ柱でない。**表示オプション**であって標準仕様には載らない。隠蔽が脅威モデル上要るなら柱7(担体)へ吸収。

## 削る地図(結論)

| 区分 | 柱 | 扱い |
|---|---|---|
| **✅ 対称発行コア(1個に束ねる)** | 1(KDF)+9(AEAD鎖)+5(ratchet)+10(最小開示) | 最小核として切り出し。10/5 は簡約・用途吟味 |
| **🎯 証明書の本命(前面)** | 4d 公開鍵 Ed25519 | 一文・キラーデモの主役 |
| **⭐ 固有価値(署名では出せない・残す)** | 3 秘匿突き合わせ / 4b 閾値発行 / 7 担体 ECC | 差別化。真の閾値署名は 4b-ii(threshold.js・しきい値Schnorr)で実装到達。BLS は将来 |
| **🧊 今は不要(野心・別腹・将来)** | 4c Fuzzy / 6 subliminal / 7 リプレイ防止 | ユースケース未接続。6 は監査で警戒も |
| **✂️ 柱でない(格下げ/吸収)** | 2 eyeglyph(表示) / 8 煙(既存監査ログ) / 10(設計原則) | 標準仕様の「柱」から外す |

**含意**: 「10柱」は標準仕様としては **コア1 + 本命1 + 固有価値3 ≒ 実質5本** に絞れる。
残りは「将来拡張」「設計原則」「運用規約」「表示」へ再配置。これは後退でなく**仕様の強度向上**。

**一文への含意**: 主語は 4d(公開鍵で誰でもオフライン検証)+ 4a/9(発行者しか作れない)+ 8(改ざんは監査ログに残る)。
固有価値(3/4b/7)は「さらに」で足す第二文。→ 例:
> 「証明書に、**発行者しか作れず・誰でも公開鍵でオフライン検証でき・改ざんは監査ログに残る**暗号的裏付けを、依存ゼロで載せる。さらに拠点単独では偽造できず(閾値)、物理媒体を経ても壊れない(ECC担体)。」

**確定一文(2026-07-02・懐疑 3 レンズ〔学術暗号/COTS 対案構成/監査+可読性〕の敵対的レビューで選定。README 冒頭・白書 §1 冒頭と同一文)**: 上の旧例は「壊れない」(実測と矛盾する絶対語)・「偽造できず」(発行不能との概念混同)・冒頭が EUF-CMA 署名の再記述、の三点で棄却。確定版は譲歩先行+公開検証層の自層内包+主張二点化(封印本体・閾値発行)+担体は実測エビデンスへ降格:
> 「公開できる事実の真贋なら、既存の電子署名で足りる——human cord はその公開検証層(Ed25519・ブラウザだけで誰でもオフライン検証)を自身の一層として備える。その上に、署名単体では出せない二つ——本体を封じたまま発行者だけが真贋を判定できる封印本体と、単一拠点では発行できない閾値発行——を一度の発行で同じ一枚に束ね、紙に印刷しスマホで撮影しても検証まで戻ることを実測してある(依存ゼロ)。」
